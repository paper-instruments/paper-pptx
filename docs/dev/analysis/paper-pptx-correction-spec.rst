paper-pptx Correction and Boundary Specification
================================================

:Status: Proposed
:Target release: 0.2.0
:Applies to: paper-pptx 0.1.2 and the ``gavin/docs-readme`` / ``codex/simplify-readme`` documentation stack
:Primary goal: Keep the parts of the fork that prevent real presentation damage while correcting compatibility breaks, incomplete appearance guarantees, unproven claims, and release-evidence gaps.


Executive decision
------------------

Keep the hard fork. Stock python-pptx 1.0.2 does not provide the relationship-safe slide,
package-preservation, anchored-editing, or verification primitives needed for reliable edits to
existing presentations. The production task evidence also shows that ``inspect_text()``,
``replace_text_at()``, and ``patch_save()`` form a useful agent workflow: the intended edit was
limited to the selected slide XML parts, and a final correction changed only one slide part.

Do not keep the current claims or boundaries unchanged. The fork is not a strict superset of
python-pptx, ``bake`` does not yet preserve every aspect of appearance, slide IDs are not permanent,
and the release process has not produced the native-PowerPoint evidence required by its own rules.
Some safety mechanisms also apply more broadly or earlier than necessary.

The correction has four outcomes:

1. Preserve upstream call compatibility unless a documented Paper safety policy explicitly refuses.
2. Make every safety and appearance claim no broader than the properties and package structures the
   implementation actually verifies.
3. Require evidence from real producer-authored presentations before declaring PowerPoint fidelity.
4. Reduce the long-term fork surface by separating the package kernel from optional agent workflows.


Definition of done
------------------

This proposal is complete when all of the following are true:

* Ordinary python-pptx calls, including saves to write-only streams, retain their upstream behavior.
* Path saves remain atomic. Atomic stream replacement is available when the destination supports it,
  but is not imposed on ordinary write-only streams.
* Read-only inspection can open a structurally valid deck containing unreachable parts. A save that
  would drop those parts either preserves them or refuses before publishing.
* ZIP resource limits are explicit and configurable rather than undocumented global policy.
* No safety decision depends on matching human-readable diagnostic prose.
* ``bake`` either materializes and verifies every property in its declared coverage or refuses before
  detaching placeholder inheritance.
* Rebind/import reports distinguish verified font changes from paragraph, list, text-frame, geometry,
  and shape-format changes. An empty report never means more than the report actually measured.
* Deck diff documentation describes its identity strategy and ID-recycling hazard accurately.
* Mixed paper-pptx/python-pptx installations fail loudly wherever the fork code can detect them, and
  the doctor remains the authoritative installation check.
* Tests never compare complete ZIP outputs whose timestamps can differ.
* The corpus includes human-authored PowerPoint inputs and Google Slides exports, with human-verified
  sidecars for appearance-dependent expectations.
* The release PR records the desktop PowerPoint checklist and links every required artifact.
* Every new release tag points to one distinct, reviewed release commit.
* The README, RST, contributor guide, API docs, and package behavior describe one consistent contract.


Current evidence and limits
---------------------------

The implementation has strong automated evidence:

* The Paper-specific local suite currently passes 850 tests.
* The complete inherited and Paper suite passed in the 0.1.2 release work.
* Changed-part budgets, save/reopen tests, relationship checks, and LibreOffice load smoke cover many
  supported operations.
* The production eval contains a successful preservation-oriented PPTX workflow using Paper APIs.

This evidence does not establish all current claims:

* The immutable eval did not include a matched stock-package control. It demonstrates the Paper
  mechanism, not package-only causality or a task-score improvement.
* The fixture corpus has no desktop-PowerPoint-authored or Google-exported fixtures.
* Current LibreOffice fixtures are round-trips of decks generated by this repository.
* Appearance sidecars are marked ``UNVERIFIED`` where a human has not checked PowerPoint rendering.
* The 0.1.2 release PR did not record the repository's required desktop PowerPoint checklist.
* Tags ``v0.1.0``, ``v0.1.1``, and ``v0.1.2`` resolve to the same bootstrap commit. Historical tags
  must not be rewritten, but this anomaly must be documented and not repeated.


Contract terminology
--------------------

The project must stop using one phrase to cover incompatible promises.

``API-compatible``
    Existing public imports, method names, arguments, return conventions, and accepted ordinary I/O
    shapes continue to work.

``Safety divergence``
    Paper deliberately refuses an input or operation that stock python-pptx attempts. Each divergence
    must be documented, typed, tested, and narrow enough to prevent a named loss or corruption mode.

``Atomic path save``
    A path destination is replaced only after a complete candidate has been written successfully.

``Atomic stream replacement``
    A readable, seekable, truncatable destination is restored after a failed publish. This is not the
    behavior of an arbitrary write-only stream and must not be described as normal stream semantics.

``Package preservation``
    Parts outside the intended edit remain byte-identical or semantically identical according to a
    documented comparison. The claim applies only to parts admitted by the selected package policy.

``Appearance coverage``
    The exact set of geometry, run, paragraph, list, text-frame, fill, line, and effect properties an
    operation resolves, materializes, and compares. ``Appearance preserved`` is valid only when the
    operation covers every property that can change in the supported structure.

``Lineage slide ID``
    The presentation-local ``p:sldId/@id`` used to align related versions of a deck. It is not a
    permanent identity and can be recycled after deletion.


Required implementation changes
-------------------------------


1. Restore the stream-save compatibility contract
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Problem
^^^^^^^

The current stream-save implementation requires a destination to be readable, seekable, and
truncatable. Stock python-pptx accepts a writable stream. The implementation also applies the input
package compressed-size limit to the previous contents of a destination stream, even though those
contents are being replaced.

Required design
^^^^^^^^^^^^^^^

Change ``Presentation.save()`` / ``OpcPackage.save()`` to use capability-based behavior:

* Paths use atomic sibling-file replacement by default.
* Readable, seekable, truncatable streams may use atomic replacement by default.
* Write-only or non-seekable streams use the upstream direct-write path by default.
* Add an explicit ``atomic`` option without breaking existing calls:

  * ``atomic=None`` selects the capability-based default.
  * ``atomic=True`` requires an atomic-capable destination and refuses before writing otherwise.
  * ``atomic=False`` uses the upstream direct-write behavior.

* Do not apply input-package resource limits to the old destination contents. If rollback snapshots
  need a resource policy, give them a separate configurable spool policy and allow disk spill.
* Preserve destination position on both success and refusal whenever the destination supports
  positioning.

Acceptance tests
^^^^^^^^^^^^^^^^

* A write-only stream accepted by python-pptx is accepted by Paper with ``atomic=None``.
* A non-seekable upload stream receives a valid package.
* ``atomic=True`` refuses an unsupported stream before the first write.
* Failed path and atomic-stream publishes restore the original destination exactly.
* Existing stream contents larger than the package intake limit do not cause an unrelated refusal.

Target files
^^^^^^^^^^^^

* ``src/pptx/presentation.py``
* ``src/pptx/opc/package.py``
* ``tests/opc/test_package.py``
* ``tests/paper/test_package_io_hardening.py``


2. Separate malformed-package validation, resource policy, and preservation policy
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Problem
^^^^^^^

Package loading currently combines three different decisions:

* whether the ZIP/OPC structure is malformed or ambiguous;
* whether expanding it exceeds fixed resource limits; and
* whether ordinary serialization would drop an unreachable physical part.

Rejecting an unreachable part during load prevents read-only inspection of producer-authored decks
that could be inspected safely. Fixed limits can also reject legitimate media-heavy presentations.

Required design
^^^^^^^^^^^^^^^

Introduce an explicit immutable package policy. The exact public name may change during API review,
but it must express these independent choices:

.. code-block:: python

   PackagePolicy(
       limits=PackageLimits(...),
       unreachable_parts="preserve-or-refuse-on-save",
       duplicate_members="refuse",
       path_traversal="refuse",
   )

Rules:

* Always reject malformed central directories, traversal names, duplicate canonical names, missing
  relationship targets, decompression-limit breaches, and XML parsing hazards before exposing XML.
* Permit valid unreachable physical parts during load and record them in a package ledger.
* ``inspect_*`` and ``diff_*`` must operate without requiring a save.
* ``patch_save()`` must copy recorded unreachable parts byte-for-byte unless the caller explicitly
  removes them.
* Ordinary ``save()`` must preserve the recorded parts or raise a typed pre-publish refusal explaining
  what would be lost. Silent dropping is forbidden.
* Resource limits must have documented defaults and an explicit override for trusted large decks.
* Overrides must not disable structural checks such as path traversal or duplicate-name detection.
* Policy and limit values must appear in refusal payloads and diagnostic output.

Acceptance tests
^^^^^^^^^^^^^^^^

* A valid deck with an unreachable custom part opens and can be inspected.
* ``patch_save()`` retains that part byte-for-byte.
* A save path that cannot preserve it refuses before changing the destination.
* A trusted policy can open a valid package above the default media limit.
* Malicious ZIP fixtures remain refused under every policy.

Target files
^^^^^^^^^^^^

* ``src/pptx/_zipguard.py``
* ``src/pptx/opc/package.py``
* ``src/pptx/package.py``
* ``src/pptx/errors.py``
* ``tests/paper/test_package_io_hardening.py``
* ``tests/paper/test_package_kernel.py``


3. Replace prose-based safety predicates with structured resolution state
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Problem
^^^^^^^

``_resolved_run_values()`` detects unsafe font-name and color cases by searching human-readable
``provenance.detail`` strings for text such as ``"non-Latin"`` and
``"unapplied transforms"``. A wording change can disable a safety refusal without changing a type or
failing a test.

Required design
^^^^^^^^^^^^^^^

* Add structured issue codes to effective-value resolution, for example:

  * ``NON_LATIN_TYPEFACE_UNRESOLVED``
  * ``COLOR_TRANSFORMS_UNAPPLIED``
  * ``THEME_MAPPING_AMBIGUOUS``
  * ``INHERITANCE_SOURCE_MISSING``

* Keep ``detail`` only as an explanation for humans.
* Require bake, rebind, import, and full diff to branch on issue codes and typed resolution state.
* Include issue codes in ``to_dict()`` payloads and version their schemas.
* Add a test that changes explanatory prose while preserving issue codes and confirms behavior is
  unchanged.
* Prohibit production safety decisions based on substring matches against diagnostic messages.

Target files
^^^^^^^^^^^^

* ``src/pptx/inspect.py``
* ``src/pptx/compose.py``
* ``src/pptx/rebind.py``
* ``tests/paper/test_effective_inspect.py``
* ``tests/paper/test_import.py``
* ``tests/paper/test_rebind.py``


4. Make bake conservative before making it complete
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Problem
^^^^^^^

Current bake behavior materializes placeholder geometry and six run-font facets: size, name, color,
bold, italic, and underline. It then removes placeholder inheritance. It does not currently prove
preservation of paragraph alignment, indentation, spacing, bullet/list state, text-frame properties,
shape fill/line/effects, or every theme-dependent value. The shift detector observes the same narrow
run-font surface, so an empty ``run_shifts`` can coexist with an unreported appearance change.

Phase A: safe correction
^^^^^^^^^^^^^^^^^^^^^^^^

Keep the public ``mode="bake"`` spelling for compatibility, but narrow its accepted structures:

* Build an ``AppearanceSnapshot`` before mutation.
* Inventory every property inherited through the placeholder that will be detached.
* If any inherited property falls outside implemented bake coverage, raise
  ``UnsupportedStructureError`` before mutation.
* Do not remove ``p:ph`` until the post-bake snapshot is equivalent for every covered property.
* Rename documentation from “freeze appearance” to “materialize supported appearance properties.”
* State the exact coverage in the API reference and report payload.

Phase B: expand appearance coverage
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

Extend the resolver and baker in this order:

1. Paragraph alignment, level, margins/indentation, line spacing, space before/after.
2. Bullet state, glyph/auto-numbering, font, color, and list-level inheritance.
3. Text-frame margins, vertical anchoring, wrapping, and autofit state.
4. Shape fill, line, and supported effects.
5. Theme and color-map dependencies for every newly covered property.

Each property group must include provenance, typed unresolved state, preflight refusal, materialization,
post-bake comparison, producer-authored fixtures, and PowerPoint verification before it becomes part of
the public preservation claim.

Report changes
^^^^^^^^^^^^^^

* Keep ``run_shifts`` for compatibility, but define it as run-font shifts only.
* Add ``appearance_shifts`` grouped by ``geometry``, ``run``, ``paragraph``, ``list``, ``text_frame``,
  and ``shape``.
* Add ``coverage`` and ``unresolved`` fields to ``ImportReport`` and ``RebindReport``.
* Increment the serialized report schema version.
* Never use an empty ``run_shifts`` as proof of complete appearance preservation.

Acceptance tests
^^^^^^^^^^^^^^^^

* A placeholder with inherited paragraph alignment refuses until alignment bake support lands.
* A placeholder with inherited bullets refuses until list bake support lands.
* Every successful bake has equivalent before/after snapshots across its declared coverage.
* Injected failures restore the placeholder element and all existing proxies.
* Native PowerPoint checks confirm each newly supported property group.

Target files
^^^^^^^^^^^^

* ``src/pptx/compose.py``
* ``src/pptx/rebind.py``
* ``src/pptx/inspect.py``
* ``src/pptx/text/bullet.py``
* ``tests/paper/test_import.py``
* ``tests/paper/test_rebind.py``
* ``tests/paper/test_effective_inspect.py``
* ``tests/paper/test_bullets.py``


5. Correct deck identity and diff semantics
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Problem
^^^^^^^

``diff_decks()`` aligns slides using presentation-local ``p:sldId/@id``. The implementation correctly
documents that the highest ID can be recycled, but user documentation calls this a permanent ID.

Required design
^^^^^^^^^^^^^^^

* Rename the concept in documentation and report descriptions to ``lineage slide ID``.
* Preserve the existing numeric ``slide_id`` field for compatibility.
* Add ``identity_strategy`` to ``DeckDiff`` and its serialized payload.
* Emit a diagnostic when an ID-recycling pattern can be inferred but not resolved.
* Investigate ``a16:creationId`` as an optional identity strategy. Do not make it the default until
  PowerPoint, Google Slides, LibreOffice, clone, import, delete, and round-trip behavior is covered by
  fixtures.
* Independently authored decks remain outside the default lineage contract.

Acceptance tests
^^^^^^^^^^^^^^^^

* Delete-highest-then-add remains a documented ambiguous case rather than a silent permanence claim.
* Existing serialized consumers continue receiving numeric ``slide_id`` values.
* Documentation examples use only lineage-derived decks unless an alternate strategy is selected.

Target files
^^^^^^^^^^^^

* ``src/pptx/diff.py``
* ``src/pptx/slideops.py``
* ``tests/paper/test_diff.py``
* ``tests/paper/test_shape_surgery.py``


6. Strengthen mixed-install detection without overstating it
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Problem
^^^^^^^

The metadata guard works only when Paper's ``pptx/__init__.py`` is the file imported. If stock
python-pptx overwrites it, the guard cannot run. Calling the import check absolute is misleading.

Required design
^^^^^^^^^^^^^^^

* Keep the import-time metadata guard as a best-effort early failure.
* Make ``paper-pptx-doctor`` the authoritative check and say so consistently.
* Define a runtime sentinel in Paper's ``pptx.__init__``.
* Have fork-only public modules verify that sentinel before importing internal collaborators. This
  catches more mixed installations where some Paper files survive beneath a stock ``__init__``.
* Ensure the doctor verifies distribution metadata, module origin, fork sentinel, and RECORD hashes.
* Add installation-order tests for Paper-then-stock and stock-then-Paper in isolated environments.
* Do not claim that Python packaging can make two distributions safely own the same import tree.

Target files
^^^^^^^^^^^^

* ``src/pptx/__init__.py``
* ``src/pptx/_version.py``
* ``src/paper_pptx_doctor/__init__.py``
* ``tests/paper/test_distribution_doctor.py``


7. Fix the ZIP-byte test and enforce the test contract
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Problem
^^^^^^^

``test_source_is_never_mutated_and_imported_chart_is_independent`` compares complete ZIP outputs.
ZIP entry timestamps make this time-dependent, and the test contradicts the rule in
``tests/paper/contract.py``. This caused real CI failures on Python 3.9 and 3.13.

Required design
^^^^^^^^^^^^^^^

* Replace the whole-package assertion with member-by-member byte comparison using the contract
  helpers.
* Compare in-memory state separately when the test intends to prove the source object was untouched.
* Add an AST-based contract test that rejects equality comparisons between complete save outputs.
* Permit whole-file byte comparison only for the same untouched input path or for explicit atomic
  refusal tests where no save occurred.
* Document the allowed comparison forms next to the helper APIs.

Acceptance tests
^^^^^^^^^^^^^^^^

* The test passes across a ZIP timestamp boundary.
* The guard test fails on a deliberately introduced whole-save comparison.
* Per-member comparison still detects any changed XML or binary payload.

Target files
^^^^^^^^^^^^

* ``tests/paper/test_import.py``
* ``tests/paper/contract.py``
* ``tests/paper/test_contract_harness.py``


8. Retain transaction correctness and add a batch/performance boundary
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Problem
^^^^^^^

``PackageTransaction`` provides valuable proxy-preserving rollback and reopen validation. It also
snapshots reachable state and serializes/reopens the complete package for every outermost transaction.
The cost is structurally package-wide, but its practical magnitude has not been measured.

Required design
^^^^^^^^^^^^^^^

Do not weaken rollback or candidate validation based on speculation. First add measurement and a safe
batching path:

* Add benchmarks for 10 MiB, 50 MiB, and 200 MiB decks with representative XML, images, charts, and
  embedded workbooks.
* Measure open, snapshot, one micro-edit, validation, rollback, save, peak RSS, and repeated-edit cost.
* Add a public or explicitly supported batch context, for example:

  .. code-block:: python

     with prs.transaction():
         replace_text_at(...)
         picture.replace_image(...)
         chart.replace_data_safe(...)

* Nested Paper operations share one outer snapshot and perform one candidate reopen at commit.
* A failure anywhere in the batch restores the entry state and preserves existing proxies.
* Keep full validation for compose, clone, import, rebind, scrub, and relationship surgery.
* Consider operation-local validation for proven micro-edits only after benchmarks and fault-injection
  tests show equivalent safety.
* Expose transaction timing in an opt-in diagnostic hook, not normal stdout.

Acceptance tests
^^^^^^^^^^^^^^^^

* A successful batch performs one outer candidate reopen.
* Failure in the last operation restores changes from all earlier operations in the batch.
* Nested transaction behavior remains deterministic.
* The release PR records benchmark numbers and the decision they support.

Target files
^^^^^^^^^^^^

* ``src/pptx/_transaction.py``
* ``src/pptx/presentation.py``
* ``tests/paper/test_transaction.py``
* a checked-in benchmark under ``tests/perf/`` or the repository's selected benchmark location


9. Build a producer-authored and human-verified corpus
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Problem
^^^^^^^

Self-generated fixtures and LibreOffice round-trips prove internal consistency but do not exercise
the producer quirks found in real PowerPoint and Google Slides files. They also cannot prove visual
appearance in PowerPoint.

Required corpus
^^^^^^^^^^^^^^^

Add at least these inputs:

* ``office_authored/powerpoint_gauntlet.pptx`` authored manually in a supported desktop PowerPoint
  version, not generated by Paper.
* ``google_export/google_gauntlet.pptx`` authored in Google Slides and exported as PPTX.
* A media-heavy but valid PowerPoint deck near the default resource thresholds.
* A PowerPoint deck containing benign unreachable/custom parts if PowerPoint preserves such a case.
* Separate focused fixtures for inherited paragraph formatting, bullets, theme colors with transforms,
  grouped/table text, charts with workbooks, notes, footers/fields, sections, shared media, and
  slide-identity behavior.

Each sidecar must record producer, exact version, OS, authorship steps, feature ground truth, human
verifier, and verification date. Appearance-dependent expectations may not retain ``UNVERIFIED``.

Required output corpus
^^^^^^^^^^^^^^^^^^^^^^

For every shipped Paper mutator, produce an output derived from a real PowerPoint-authored fixture and
verify:

* clean PowerPoint open without repair;
* intended edit visible;
* unrelated slides and package parts preserved within the declared budget;
* chart/workbook editability;
* notes, live fields, bullets, crop, hyperlinks, and template inheritance where applicable;
* save-as from PowerPoint followed by successful Paper reopen.

Pixel claims require a recorded render or screenshot comparison. Structural checks must not be
described as visual proof.

Production-eval feedback
^^^^^^^^^^^^^^^^^^^^^^^^

Create a non-confidential regression fixture that reproduces the mechanism demonstrated by the
production eval: anchored edits across selected slides followed by ``patch_save()`` and an exact
changed-part budget. Do not copy proprietary task content into the repository.

10. Make native PowerPoint evidence a release gate
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Required design
^^^^^^^^^^^^^^^

* Store one evidence record per release under ``tests/paper/release-evidence/``.
* The record includes release commit, candidate artifact hashes, PowerPoint version, OS, verifier,

12. Reduce the long-term fork surface without a flag-day migration
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The current runtime delta is large. Deep OPC, relationship, and proxy changes require a fork, while
some inspection and workflow layers do not intrinsically need to live in the frozen ``pptx`` import
tree.

Target boundary
^^^^^^^^^^^^^^^

Keep in the ``pptx`` fork kernel:

* OPC load/save and package-preservation hooks;
* relationship ownership and reachability primitives;
* proxy liveness checks;
* transaction/rollback mechanics;
* relationship-safe slide, shape, chart, image, and table mutations;
* the minimum resolver hooks that require private python-pptx state;
* backwards-compatible methods already attached to core proxy classes.

Move or author new high-level workflow code under a ``paper_pptx`` companion namespace:

* inspection manifests and report schemas;
* anchored multi-step editing workflows;
* deck/package diff orchestration;
* scrub policy orchestration;
* doctor and diagnostics;
* future batch workflows and evaluation receipts.

Treat these as experimental until the producer corpus and appearance coverage are complete:

* bake-based cross-template composition;
* layout rebind with appearance guarantees;
* destructive scrub combinations;
* Header & Footer dialog equivalence and live-field synchronization claims.

Migration rules
^^^^^^^^^^^^^^^

* Do not move existing imports during the 0.2.0 correctness release.
* Introduce the companion namespace and forwarding shims after the corrected contracts stabilize.
* Keep old ``pptx.*`` import paths working for at least two minor releases.
* Emit deprecation warnings only after the replacement API and migration guide exist.
* Do not duplicate stateful package logic across the two namespaces; the companion layer calls the
  fork kernel.
* Evaluate generic kernel improvements for upstream contribution where they do not depend on Paper's
  safety policy.


Error and report contract improvements
--------------------------------------

Every ``PaperRefusal`` used by the corrected implementation must expose structured context, not only
an exception string. At minimum, relevant subclasses should provide:

* operation;
* part name and relationship ID where applicable;
* policy or limit name;
* configured and observed values;
* unsupported structure or resolution issue code;
* whether mutation began;
* whether rollback was exact;
* safe next actions where they can be stated deterministically.

``TransactionRollbackError`` remains separate from ``PaperRefusal`` because exact restoration is no
longer proven. Documentation must instruct callers to discard the live presentation after this error.

Report schemas must be versioned. Additive fields may preserve the current version only when existing
consumers can safely ignore them; changed meanings require a new version.


Implementation sequence
-----------------------

Deliver the correction as reviewable pull requests in this order:

PR 1 — Claims and deterministic tests
    Fix the whole-ZIP comparison, add the contract guard, correct the most dangerous README/RST
    claims, and label unverified capabilities. This stops known misinformation immediately.

PR 2 — Stream compatibility
    Restore write-only stream saves, separate path/atomic-stream/direct-stream behavior, and add the
    explicit atomic option.

PR 3 — Package policy
    Separate structural validation, configurable resource limits, and unreachable-part preservation.

PR 4 — Structured resolver and conservative bake
    Replace prose predicates, add typed resolution issues and coverage, refuse unsupported inherited
    properties, and expand report schemas.

PR 5 — Identity and mixed-install corrections
    Correct lineage identity, add identity strategy metadata, strengthen sentinel checks, and expand
    isolated installation-order tests.

PR 6 — Transaction batching and benchmarks
    Add the batch boundary and measure before changing validation strength.

PR 7 — Producer corpus and release evidence
    Land real PowerPoint/Google fixtures, human verification, native-app outputs, and evidence schema.

PR 8 — 0.2.0 documentation and release
    Complete the compatibility page, publish benchmark/evidence results, record the checklist, and tag
    one distinct reviewed commit.

PR 9 and later — Companion boundary
    Introduce ``paper_pptx`` workflow modules and compatibility shims without mixing this architectural
    migration into the correctness release.


Release gates
-------------

The 0.2.0 release is blocked unless all applicable gates pass:

* inherited pytest and behave suites across supported Python versions;
* Paper contract suite and refusal fault injection;
* deterministic ZIP-member budgets;
* LibreOffice load smoke;
* producer-authored PowerPoint and Google fixture tests;
* recorded desktop PowerPoint checklist;
* isolated wheel installation in both package-install orders;
* wheel/sdist metadata and doctor checks;
* stream compatibility matrix;
* package-policy security fixtures;
* bake coverage/refusal matrix;
* transaction benchmark report;
* Sphinx warnings-as-errors;
* release evidence record matching the release commit and artifact hashes.


Explicit non-goals
------------------

This proposal does not require:

* building a PowerPoint renderer or claiming pixel-perfect equivalence;
* accepting malformed or adversarial ZIP/OPC structures;
* supporting independently authored deck alignment in ``diff_decks()``;
* fully resolving SmartArt, animations, transitions, or every AlternateContent branch;
* rewriting ``PackageTransaction`` before benchmarks identify a measured bottleneck;
* rewriting or moving published historical tags;
* proving package-only task-score superiority from the existing bundled production eval;
* moving all high-level modules out of ``pptx`` during the correctness release.


Success criteria after release
------------------------------

The corrected project should be able to make a narrower and stronger statement:

  paper-pptx extends python-pptx 1.0.2 with relationship-safe editing and package-preservation
  primitives for existing presentations. It preserves ordinary upstream calls, documents each
